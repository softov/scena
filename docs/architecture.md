# Architecture

The whole runtime is one idea taken seriously: **UI is data, and the data lives
in one store.** Everything below follows from that, including the parts that
look like ceremony.

A conventional React application expresses a screen as a tree of imports. That
tree cannot be persisted, sent over a wire, edited by a person who is not a
programmer, or generated by something that is not a compiler — because half of
it is module identity. Scena expresses the same screen as a graph of nodes that
name their components, and resolves those names at mount time.

```
   a ComponentNode graph          the registries              the shell
   ─────────────────────          ──────────────              ─────────
   { component: 'Column',    →    components.get('Column')  →  mounted into
     children: [...] }            commands.get('save')         sidebar:left
          │                       converters.get('date')       by a layout
          │
          └── props read through binding paths → the reactive store
```

## The store

`ReactiveStore` is a single tree, addressed by JSON-Pointer-shaped paths, and
it is the only place state lives.

```
$/tickets/view          the window a list currently shows
$/tickets/byId/66110    one record
$/summary/tickets/total a derived count
$/active/id             what is selected, application-wide
$/modus/class           the display environment
```

The first segment is a **scope**, and scopes are lifetimes rather than folders.
`local` dies with the mount, `page` with the page, `workspace` and `global`
outlive both, `summary` holds derived counts, `active` holds selection, `ui`
and `layout` hold chrome, and `plugins.<name>` is a namespace a contributor
owns. `clearNamespace` is what makes sign-out a single call.

Three things are layered on top:

- **`computed(path, def)`** — a path derived from other paths, recomputed when
  they change. `{ from: [...], select }`.
- **`registerDataProvider(def)`** — a namespace, and the code that fills it.
  Providers are lazy by default: nothing fetches until something reads.
- **`SocketBridge`** — the transport handed to providers. Scena does not care
  whether it is a WebSocket, SSE, or a poll behind an adapter; it cares that
  events arrive with names.

A **relative** path (`/title`) resolves against the surrounding data context,
which is what lets one templated node render a hundred rows. `..` is forbidden
on purpose: escape to the root with `$/` instead, so a node's meaning does not
depend on where it was pasted.

## The component graph

A page *is* its root `ComponentNode`:

```jsonc
{
  "component": "Column",
  "gap": 12,
  "children": [
    { "component": "Heading", "text": { "path": "/title" } },
    { "component": "Listable",
      "items": { "path": "$/tickets/view" },
      "onSelect": { "functionCall": { "call": "tickets.open" } } }
  ]
}
```

Prop values are literals, **bindings** (`{ path }`), or **function calls**
(`{ call, args }`). Children are an inline array, or a template plus a path —
one instance per item, each with its own data context. Actions are
discriminated by key presence: an `event` is routed to the server, a
`functionCall` runs a registered command.

`id`, `component` and `$meta` are reserved on every node. Everything else is
props, and props are the component's business.

## The registries

Late binding is the mechanism the whole design rests on. Each registry maps a
name to a thing, and every lookup happens at mount time.

| Registry | Maps | Contributed by |
| --- | --- | --- |
| `components` | `'Listable'` → a React component + props schema | the catalog, or an app |
| `commands` | `'tickets.open'` → a function, args schema, `when` clause | anything |
| `keybindings` | a chord → a command id, scoped to a surface or view | anything |
| `converters` | `'date'` → a value transform | anything |
| `layouts` | `'tabs'` → a surface render strategy | built in, or an app |
| `shells` | `'default'` → the outermost frame | built in, or an app |
| `mountMenus` | a menu slot → context-menu rows | anything |
| `surfaces` | a surface name → its mounts | the app, at runtime |

Two consequences are worth stating plainly. A name that was never registered
is a runtime miss, not a compile error — which is the price of the graph being
data. And a command is the *only* way an action should be spelled: a button
that calls an API directly and a slash command that calls the same API are two
implementations that will drift, while a button that runs a registered command
cannot drift from the command.

`permissions` and the `when` engine sit across all of it. A `when` clause is a
small expression over store paths, so chrome that should not exist for this
user does not mount rather than mounting disabled.

## Surfaces, mounts and layouts

A **surface** is a named region. scena ships nine names — `titlebar`,
`activitybar`, `sidebar:left`, `sidebar:right`, `main`, `panel:bottom`,
`statusbar`, `overlay`, `detached` — because they are the vocabulary
`DefaultShell` draws, `layout` seeds defaults for, and a keybinding scope
shares.

They are a **convention, not the set**. A surface is whatever an app mounts to:
mounts, layout state and store paths are all keyed by the string, so an app may
define `alert:top`, a second status bar, four sidebars, or no sidebar at all,
and only its own shell needs to know how to draw them.

The consequence is for anything that sweeps surfaces rather than addressing
one: ask `surfaces.listSurfaces()`, which reports what is actually occupied. A
list of names written into scena cannot know what an app defined — the session
snapshot iterated one for a while, and dropped mounts on app-defined surfaces
with no error.

A **mount** is one component in one surface, under a key, with:

- a `MountTarget` — an inline node, or a binding whose value is a node
- `MountDisplay` — title, icon, colour, header actions; per mount, so two
  instances of one component can be "Chat A" and "Chat B"
- `MountPolicy` — editable, persistent, transient, customizable

A **layout** decides how a surface's several mounts are shown: `Tab`,
`TabPanel`, `Single`, `Split`, `Stack`, `Spatial`, `Rail`, `Inline`, `Bar`,
`Floating`. Which layout a surface uses is store state, so it is switchable at
runtime and persistable per user — `LayoutStorage` is the interface, and
`createLocalStorageLayoutStorage` the obvious implementation.

A **shell** is the frame around the surfaces. It receives `scena`, the active
layout, and a `renderSurface(name)` function; where it puts the results is the
whole of what a shell decides.

A **session snapshot** is the mounts, the surface states and the persisted
context, captured together. Restoring one is how a reload comes back to the
same three tabs open in the same order.

## Porta: the sign-in surface

`Limen` is a wall: it renders its children only once a session with the
required permission exists. `Sigillum` is that session in the store.
A **provider** is what exchanges credentials for one — a token pasted into a
form, an OAuth round trip, whatever the application has.

The design point is that authentication is a *provider*, not a fork in the
application. An app registers one and the wall does the rest, which is why
sign-out is `clearNamespace` and not a cascade of resets.

## Modus: the environment as state

Screen size, orientation and pointer accuracy are published into `$/modus/*`
by a scope backend. A presentation policy then reads store state to decide
whether the sidebar is a sidebar or a sheet.

This is deliberately not media queries. A media query can style a component
but cannot decide whether it should be mounted at all, and "on a phone this
surface is not a surface" is a mounting decision.

## The React bindings

`@softov/scena/react` is a thin layer:

- `Scena` — the provider. Takes options (layout storage, scope backends, the
  socket) and an `onRender(scena)` hook for boot-time registration.
- `SurfaceArea` — renders one surface through the active layout.
- `ViewMount` — renders one component graph, resolving bindings and templated
  children.
- `useScena()`, `useStore(path)` — the two hooks most application code needs.

`useStore` subscribes to one path and re-renders on it. A component that reads
the store into `useState` and then edits the copy has created a second answer
to a question the store already answers; the store is authoritative, and the
only reason to hold local state is something that has not been committed yet —
the text in a composer before it is sent.

## What is deliberately not here

- **No router.** Surfaces and mounts are the navigation model. An app that
  wants URLs maps them onto mounts itself.
- **No data-fetching opinion.** A data provider is a function that fills a
  namespace; whether it uses `fetch`, a socket, or a cache is not scena's
  business.
- **No styling framework.** CSS custom properties (`--oo-*`) and plain
  stylesheets shipped beside their components.
- **No server.** The graph is data and could come from a server, but nothing
  here requires one.
